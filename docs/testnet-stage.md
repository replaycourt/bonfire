# Bonfire on testnet: the staging run

Before the final keyless launch, the contract ran on a staging account on NEAR testnet with the testnet launch values (five-minute nights) and the five demo bots, and a scripted end-to-end run checked it against an independent model of the rules after every transaction. This file says what ran, lists every transaction, and gives the real gas.

**Result:** no contract bug found. Every check passed in the clean run (details below). The two aborted attempts before it failed for one reason outside the contract: the machine running the script went to sleep in the middle of a night.

- `config()` returns exactly the init arguments: the `testnet` block of `sim/params.json` with one change, `max_accounts`.
- Right after `new`: supply 1,000,000 EMBER, hearth 900,000, the five bots with 40,000 / 30,000 / 15,000 / 5,000 / 10,000, `audit()` balanced and ledger true, 291,186 bytes of storage.

**`max_accounts` = 1,773 instead of 4,505.** `scripts/deploy.mjs` lowers it so that the worst-case storage stake of `contract/README.md` ("Storage") fits the account's balance less a 0.1 NEAR reserve:

```
room   = (10.0000 NEAR - 0.1 NEAR) / 10^19 yocto per byte          = 990,000 bytes
fixed  = code 289,280 + the account's own record and key 182 + root 2,600 + 84 * 5 founders
         + 472 * log_keep 48 + 2,257 * history_keep 4,096 / 32
         + 246 * 48 (room for log_keep settled nights nobody collects) = 615,842 bytes
max_accounts = floor((990,000 - 615,842) / 211)                    = 1,773
```

The worst case is then 989,945 bytes, 9.90 NEAR of stake. `config().account_storage_bytes` measured at init is 211, as assumed. The full testnet value (4,505) makes the worst case about 1.57 MB, 15.7 NEAR of stake with the code, so the final account needs about 16 NEAR to keep it.

## Scripts

All in `scripts/`, Node 20+ and no dependencies. Testnet accounts only; every key they make goes to the git-ignored `.secrets/` with mode 600.

| Script | What it does |
|---|---|
| `near-lite.mjs` | RPC client (FastNEAR, dRPC as fallback), transaction signing and borsh for function calls, deployment and access keys; adapted from Lantern Row's |
| `bonfire-lib.mjs` | secrets, the relay pool, browser-style players that sign `act`, and a model of the settlement arithmetic written from DESIGN.md and the README formulas |
| `setup-gas-pool.mjs <gas account> <contract> <n> [allowance]` | adds `n` function-call keys (`act`, `settle`, `collect`) in one transaction |
| `deploy.mjs <account> [--wasm] [--max-accounts] [--reserve] [--lock]` | deploys and calls `new` in one transaction, makes the bot keys, lowers `max_accounts` to fit the balance, checks the code hash, `config()` and `audit()`; `--lock` deletes every access key afterwards (not used on staging) |
| `bots.mjs <contract> --nights N [--seed] [--always] [--smoke k] [--cold k] [--quiet k]` | the five demo bots as `sim/params.json` describes them; they settle when a night is due and collect, each by a different path; exits after N nights |
| `e2e-stage.mjs <contract> --out <dir> [--nights 8]` | the scripted end-to-end run below |

To repeat the run (it needs about 45 minutes, and the machine must stay awake):

```
node scripts/setup-gas-pool.mjs bonfire-gas.testnet bonfire-stage.testnet 8 0.5
node scripts/deploy.mjs bonfire-stage.testnet          # only once per account
caffeinate -is node scripts/e2e-stage.mjs bonfire-stage.testnet --out <dir>
```

## The end-to-end run

`scripts/e2e-stage.mjs` drives the five bots (`scripts/bots.mjs`, with every bot playing every night it may) and a visitor through eight five-minute nights, nights 11 to 18 on the chain (2026-11-06, 06:23:36 to 07:03:36 UTC). The plan:

| Run night | Chain night | Bots | Visitor (a fresh browser-style ed25519 key, `18b3f2db...2a99`) |
|---|---|---|---|
| 1 | 11 | as published | claims kindling through `act`, throws 120 in window 1 |
| 2 | 12 | as published | collects (signed `collect` action); its collect replayed; a throw naming night 13; a second kindling claim; throws 60 in window 2 |
| 3 | 13 | under-throw on purpose: the early bots throw a quarter, the steady and late bots hold back | throws 40 (its throw collects night 12 first) |
| 4 | 14 | nobody throws | collects the smoky night (signed action) |
| 5 | 15 | as published | throws 80 in window 0, beside the early bots |
| 6 | 16 | nobody calls anything, not even `settle` | nothing |
| 7 | 17 | the first `settle` settles nights 15 and 16 at once | `collect(visitor)` sent by the relay for it; throws 50 in window 3 |
| 8 | 18 | as published | nothing; collects after the night |

Every night opened with a bot calling `settle` and the bots collecting, each by its own path: demo-bot-early-a through its next throw (or a signed `collect` action when it does not throw), demo-bot-early-b and demo-bot-late through `collect(account_id)`, demo-bot-steady through a signed `collect` action. Every `act` was signed by the player's key and relayed through a gas key. Two earlier attempts stalled for 17 minutes each because the machine slept (see Surprises); their transactions are listed below, but they are not part of the checked run.

### What was checked

## Surprises

- **The machine slept.** Attempts 1 and 2 stalled for about 17 minutes each, the script frozen in the middle of a night: the Mac was in normal sleep with short dark wakes (`pmset -g log`: "Maintenance Sleep ... 979 secs"). The bots then acted on nights that had already ended, and the contract refused every such action cleanly (`the action is for night 2, but this is night 4`), still collecting what the caller was owed, as documented. The clean run kept the machine awake with `caffeinate -is`, and `bots.mjs` now stops when it falls more than half a night behind instead of acting late. Bots that run for days need a host that does not sleep.
- **dRPC's free plan does not wait for transactions.** `send_tx` with `wait_until: EXECUTED_OPTIMISTIC` answers "Request timeout on the free plan" there, so the fallback is useful for views only; `near-lite.mjs` goes back to FastNEAR for it. Right after a wake both endpoints failed for a few seconds (`fetch failed`); retries covered it.
- **Gas is about a tenth of what is attached**, see above. Function-call allowances are charged only what a call burns, about 0.0003 NEAR, so 0.5 NEAR per key lasts over a thousand calls.
- **A bot's label cannot be in its account name.** docs/SIMULATION.md says each demo bot "is labelled as a bot in its account name". The bots are implicit accounts (64 hex characters), so the label lives in `.secrets/bots-<contract>.json`, in this file and on the page.
- **A night with early wood above the target pays late wood little.** On night 11 the early bots' 339.65 EMBER in window 0 already covered the 234.37 target, so all wood of the later windows (the visitor's 120 included) counted at `late_lit`. That is the rule working as designed; with the target this low after the cold nights of the two aborted attempts, the testnet bots overshoot their fire by two to three times.
- **Wood on the burning night leaves `ft_balance_of`.** A thrower's balance drops by its wood until the night is settled and then counts the credit again: by design (the wood is on the pile), but a wallet shows the dip.

## Bugs

None found. Every on-chain result matched the model to the base unit, every refusal was the documented one, and nothing was left owed after everyone collected.
